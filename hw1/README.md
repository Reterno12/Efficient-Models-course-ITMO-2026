Работа содержит **две версии решения в одной папке**. Архитектура сети и протокол измерений одинаковы; во второй версии уточнены аналитические модели latency, energy и memory.

| Версия | Ноутбук и код | Результаты |
|---|---|---|
| **1 — исходная** | [hw1.ipynb](hw1.ipynb): исходные model, equations, measurement и calibration полностью встроены в notebook | [results_v1/](results_v1/) |
| **2 — актуальная** | [hw1_version_2.ipynb](hw1_version_2.ipynb): встроенный код соответствует текущим `.py`-модулям | [results_v2/](results_v2/) |

Все `.py` и тесты в этой папке относятся **к версии 2**. Отдельных старых `.py` нет: первую реализацию можно изучить и выполнить в автономном `hw1.ipynb`. Для продолжения работы используйте `hw1_version_2.ipynb`.

## Запуск и воспроизводимость

**Google Colab:** загрузите выбранный `.ipynb`, включите **T4 GPU** и выполните **Run all** в чистом runtime. Для обеих версий достаточно одного notebook: локальные `.py` загружать не нужно.

Версия 2 каждый раз измеряет новый прогон в `hw1/results_v2/runs/<RUN_ID>/`. При повторе ячейки измерений в той же сессии CSV дополняется с пропущенной точки. После перезапуска runtime для продолжения нужно задать прежний RUN_ID и восстановить CSV, если Colab удалил файлы. Последняя ячейка скачивает `hw1_version_2_results_<RUN_ID>.zip`. После проверки результаты выбранного прогона размещаются в корне `results_v2/`. Промежуточная папка `runs/` и скачанные ZIP не включаются в Git. Версия 1 использует `results_v1/`; существующий CSV позволяет возобновить её исходный эксперимент.

Локально из корня репозитория:

```bash
uv sync --frozen
uv run --frozen jupyter lab
```

## Модель, соглашения и измерения

Сеть: шесть блоков Conv–BatchNorm–ReLU, MaxPool после первого, GlobalAvgPool, Linear 512→256, ReLU и Linear 256→100. Convolution: padding `k//2`, bias=False; ReLU inplace. Режим — eval, `torch.inference_mode()`, FP32; случайные входы `B×3×S×S`. `cudnn.benchmark=False`, оба `allow_tf32=False` во всех прогонах.

Grid соответствует заданию: 7 базовых и 4 случайных размера S, 9 базовых и 3 случайных B — **132 конфигурации**. Seed 2026 заранее выделяет 106 train и 26 validation. OOM записывается как отдельный статус; такие строки не участвуют в fit.

- **FLOPs:** один MAC = 2 FLOPs; дополнительно учитываются BN/GAP и bias, сравнения ReLU/MaxPool исключены. PyTorch profiler оценивает Conv/Linear.
- **Memory:** `torch.cuda.max_memory_allocated()` за forward после warmup, включая модель, живой input и allocations библиотек через PyTorch allocator. CUDA context и свободные reserved blocks в эту метрику не входят.
- **Bytes moved:** сумма чтений/записей каждого оператора; weights Conv читаются один раз за forward. Cache reuse, fusion и временный workspace в traffic не моделируются.
- **Latency:** медиана семи synchronized wall-clock forwards после трёх warmup.
- **Energy:** NVML power усредняется за серию forwards, умножается на длительность и делится на число проходов. Это энергия всей GPU.

Все четыре функции принимают числа и NumPy arrays с broadcasting. FLOPs и Memory не имеют калибруемых параметров; latency/energy калибруются только на train.

## Что изменилось во второй версии

| Функция | Версия 1 | Версия 2 |
|---|---|---|
| FLOPs | Аналитический подсчёт операций | Без изменений |
| Memory | `W + 76BS²` | `W_alloc + W_BLAS + 76BS²` |
| Latency | `t0 + max(F/P, Q/R)` | `t0 + max(F/P(B), Q/R)` |
| Energy | `P_idle·T + e0 + eF·F/1e9 + eQ·Q/1e9` | `(P_idle+P_active)·T + e0 + eF·F/1e9 + eQ·Q/1e9` |

`W_alloc = 4 187 136 bytes` получается из размеров отдельных parameters/buffers с округлением до 512 bytes. `W_BLAS = 8 519 680 bytes` — стандартный workspace cuBLAS для pre-Hopper из [исходников PyTorch 2.11](https://github.com/pytorch/pytorch/blob/v2.11.0/aten/src/ATen/cuda/CublasHandlePool.cpp). Эти константы **не подгоняются по CSV**. Допущения: T4, native allocator, один stream, отсутствие workspace overrides и посторонних GPU tensors. Дополнительные cuDNN/cuBLASLt workspace остаются вне формулы.

`P(B)` использует один либо два эффективных compute rate. Модель и порог выбираются 5-fold CV внутри train по mean APE; второй режим принимается при улучшении минимум на 5%. Затем коэффициенты подгоняются на всём train. В текущем прогоне выбран `B*=64`. Энергетические коэффициенты неотрицательны; `P_idle` измеряется отдельно.

`results_v1/` содержит первоначальные измерения и коэффициенты из коммита `d04768f`. Формулы v1 сохранены; в её графике latency исправлен только перевод seconds → ms, без изменения предсказаний или ошибок. `results_v2/` содержит последний пользовательский прогон **20260927_090211_ab1cd7d2**, импортированный из `hw1_results_20260927_090211_ab1cd7d2.zip`. Его CSV и коэффициенты latency/energy сохранены без изменений. Архивная сводка ещё использовала старую формулу памяти: для v2 отчёт пересчитан актуальными модулями. Исходные CSV/theta/сводка сохранены в `results_v2/source_run/`; происхождение и хеши — в `import_manifest.json`.

## Обсуждение

Расхождение FLOPs около 0,25% ожидаемо: аналитическая формула дополнительно считает BN/GAP, а profiler — Conv/Linear. Сеть и арифметика в обеих версиях одинаковы.

Первая модель памяти пропускала постоянный workspace cuBLAS, который остаётся живым после warmup, и округление мелких allocations. Их учёт уменьшил ошибку без калибровки. Однако модель всё ещё недооценивает дополнительные workspace, зависящие от формы тензоров и выбранного cuDNN kernel. Худший validation-случай v2 — `S=32, B=256`, ошибка 68,53%. Размеры временного workspace на другой GPU нельзя переносить на T4.

Два compute rate описывают наблюдаемое замедление больших batch. При этом fitted P/R не являются аппаратными пиковыми характеристиками. В v2 по наибольшему члену формулы 98 точек относятся к compute-bound и 34 к launch-bound; memory-bound точек нет. Это классификация модели, не аппаратное измерение bottleneck. Отсутствие memory-bound области ограничивает интерпретацию R. Между измеренными B=64 и B=95 точная граница переключения также неизвестна.

Active power позволяет лучше описать энергию работающей GPU, но NVML имеет ограниченную частоту обновления. Кроме того, energy измеряется серией проходов, latency — одиночными синхронными вызовами. В новом прогоне коэффициент стоимости traffic равен нулю: данные не определяют его отдельно от остальных членов.

Нулевое число OOM не подтверждает точность границы OOM. Holdout уже использовался в предыдущих отчётах: параметры и выбор порога не подгоняются на validation, однако независимая проверка новой гипотезы требует свежих конфигураций. Цель задания — объяснить и улучшения, и оставшиеся ограничения аналитических моделей.
